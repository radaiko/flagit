Deployment

Flagit is one static binary with the frontend embedded and one SQLite file. Whatever you run it on, the shape is the same: expose :8080 to your apps, keep :3000 private, and persist /data.

Topology

Two ports, two very different audiences.

Port Serves Exposure
8080 Public API (/api/*), the web overlay, /healthz Reachable by your apps. Behind TLS — a reverse proxy, or Tailscale Funnel if you do not want a public hostname of your own.
3000 Internal API (/internal/*), admin dashboard (/internal/admin), /healthz Private. A tailnet address, or loopback plus an SSH tunnel. Never the open internet, and never a domain on the public proxy.
The admin key is the whole perimeter for port 3000. It grants read and write access to every ticket, every diagnostic log and every setting. Treat the port as privileged infrastructure even though the key is required.

Configuration

Every setting is a flag with an environment-variable fallback. Flags win, so a container can always be overridden on the command line.

Flag Environment Default Purpose
--port FLAGIT_PORT 8080 Public API and web overlay.
--admin-port FLAGIT_ADMIN_PORT 3000 Internal API and admin dashboard.
--db-path FLAGIT_DB_PATH ./data/flagit.db SQLite file. Put it on a volume.
--admin-key FLAGIT_ADMIN_KEY generated Admin credential. Left unset, one is generated and printed once on first start; only its hash is stored.
--public-url FLAGIT_PUBLIC_URL empty Externally reachable base URL, used to build the link in webhook payloads.
--commit FLAGIT_COMMIT build value, else unknown Git revision this deployment was built from, shown in the admin dashboard footer. Falls back to the SHA stamped in at build time, then to unknown.
--log-level FLAGIT_LOG_LEVEL info debug, info, warn, error.
--dev FLAGIT_DEV false Proxy the frontend to a Vite dev server instead of serving embedded files.
--vite-url FLAGIT_VITE_URL http://localhost:5173 Where that dev server lives.

The Hermes webhook URL and the auto-processing switches are not environment variables — they live in the database and are edited under Settings in the dashboard, so they can be changed without a redeploy.

Docker Compose

The repository ships a docker-compose.yml that builds the image from source: a Node stage builds the Svelte bundles, a Go stage embeds them and compiles a static binary, and the runtime stage is Alpine with a non-root user. 

git clone https://github.com/radaiko/flagit
cd flagit
docker compose up -d

# Read the generated admin key — printed exactly once.
docker compose logs flagit

The important parts of the compose file:

services:
  flagit:
    build: .
    restart: unless-stopped
    expose:
      - "8080"                      # public API — reached through a proxy, not the host
      - "3000"                      # admin — reached through the Tailscale sidecar only
    volumes:
      - flagit_data:/data
    environment:
      FLAGIT_PUBLIC_URL: ${FLAGIT_PUBLIC_URL:-https://flagit.spitzbub.app}
      FLAGIT_ADMIN_KEY: ${FLAGIT_ADMIN_KEY}

  tailscale-admin:
    image: tailscale/tailscale:latest
    restart: unless-stopped
    hostname: flagit-admin
    environment:
      TS_AUTHKEY: ${TS_AUTHKEY}
      TS_HOSTNAME: flagit-admin
      TS_STATE_DIR: /var/lib/tailscale
      TS_SERVE_CONFIG: /config/serve.json
      TS_USERSPACE: "true"
      TS_ACCEPT_DNS: "false"
    volumes:
      - tailscale_state:/var/lib/tailscale
      - ./deploy/tailscale:/config:ro
    depends_on:
      flagit:
        condition: service_healthy

volumes:
  flagit_data:
  tailscale_state:

Neither service binds a host port. expose publishes to the compose network only, which is all a reverse proxy on the same network needs, and it means no firewall rule can be forgotten. The dashboard has exactly one route in — the sidecar described under Tailscale.

For local work, an overlay publishes both ports on loopback so you can open the dashboard without a tailnet: 

docker compose -f docker-compose.yml -f docker-compose.local.yml up -d flagit
# http://127.0.0.1:8080  overlay and public API
# http://127.0.0.1:3000/internal/admin  dashboard

Naming the service is deliberate: without a TS_AUTHKEY the sidecar cannot log in and would sit in a restart loop.

docker-compose.local.yml is never loaded automatically — not by docker compose up, not by Coolify — so it cannot leak into a deployment.

Setting the key yourself. Put FLAGIT_ADMIN_KEY in a .env next to the compose file (or in your platform's secret store) and the generated-key step is skipped entirely. A key supplied this way is hashed and persisted, so a later restart without the variable still accepts it.

Coolify on a Hetzner VM

Coolify runs the same compose file; the work is in telling it which port is public, which secrets exist and where the data lives. The reference deployment below uses flagit.spitzbub.app for the public API and keeps the dashboard on the tailnet.

  1. DNS first. An A record for the public hostname pointing at the VM. Coolify cannot issue a certificate before the name resolves.
  2. New resource → Docker Compose, in your project, pointed at the repository and the main branch, with docker-compose.yml as the compose file. The Dockerfile at the root is the build.
  3. Domains: on the flagit service only, set https://flagit.spitzbub.app:8080. The port suffix tells Coolify's proxy which container port to route to; it is not published on the host. Give the tailscale-admin service no domain at all, and never map a domain to port 3000 — that would put the admin dashboard on the public internet.
  4. Environment variables: three, of which two are secrets.
    Variable Value Kind
    FLAGIT_PUBLIC_URL https://flagit.spitzbub.app Plain. Must match the domain above, no trailing slash.
    FLAGIT_ADMIN_KEY a long random string you generate Secret (“Is Build Variable?” off, value hidden). Required in this deployment: the dashboard is the whole internal API.
    TS_AUTHKEY tskey-auth-… from the Tailscale admin console Secret. Consumed once, on the sidecar's first start.
  5. Persistent storage: the compose file declares the named volumes flagit_data (mounted at /data, the SQLite file) and tailscale_state (at /var/lib/tailscale, the tailnet identity). Coolify creates both; confirm they are listed under Storages before the first deploy. Without the first, every redeploy starts from an empty database. Without the second, every restart burns a new device on your tailnet.
  6. Healthcheck: the image already defines one against /healthz on 8080, which is unauthenticated precisely so this works. The sidecar waits for it before starting.
  7. The deployed commit needs no configuration. Coolify sets SOURCE_COMMIT to the revision it just deployed, and the compose file maps it onto FLAGIT_COMMIT for the container. The dashboard footer then shows the short SHA, with the full one on hover and behind the copy button. There is nothing to add to the environment list; if you ever want to pin it by hand, set FLAGIT_COMMIT explicitly and it wins.
  8. Deploy, then check both services: curl the public health endpoint, and open the dashboard over the tailnet. 
curl -s https://flagit.spitzbub.app/healthz
{"data":{"status":"ok"}}

# From any device on the tailnet
open https://flagit-admin.<tailnet>.ts.net/internal/admin

# Which commit is actually running? The dashboard footer answers this, and so
# does the endpoint behind it. Admin key required; it is not on the public API.
curl -s -H "X-Admin-Key: $FLAGIT_ADMIN_KEY" \
  https://flagit-admin.<tailnet>.ts.net/internal/version
{"data":{"commit":"212b000f1e…","short":"212b000","known":true}}
Why runtime and not a build argument. Coolify deliberately keeps SOURCE_COMMIT out of Docker builds so the build cache survives a commit that changed nothing relevant; including it is an opt-in (Include Source Commit in Build, in the application's General settings), and for the Docker Compose build pack build variables are passed by --env-file rather than as --build-arg. Taking the value at runtime sidesteps both: every deploy reports its revision, and no build is invalidated. The GIT_COMMIT build argument in the Dockerfile remains for make docker and other builders, and is only a fallback — the runtime value wins.
Do not publish ports from this compose file. Adding a ports: entry — for either service — binds it on the VM's public interface and bypasses the proxy entirely. Port 3000 in particular has no business on the host. The same goes for the VM firewall: only 80 and 443 belong open. Coolify's own dashboard on 8000 and SSH should be reachable over your tailnet or a trusted source range, not from the internet.

If the sidecar is down and you need the dashboard anyway, port 3000 is not on the host, so an ssh -L tunnel has nothing to attach to. Put a throwaway relay on the compose network for as long as you need it: 

# On the VM: bridge loopback:3000 to the container, and stop it when you are done.
docker run --rm --network <coolify-compose-network> -p 127.0.0.1:3000:3000 \
  alpine/socat tcp-listen:3000,fork,reuseaddr tcp:flagit:3000

# From your machine
ssh -L 3000:127.0.0.1:3000 you@your-vm

Tailscale

Tailscale solves both halves of the exposure problem: a private path to the dashboard, and an optional public path to the API without owning a domain.

Private: the admin dashboard on your tailnet

The compose file ships a sidecar for this — a Tailscale node of its own, named flagit-admin, that reverse-proxies exactly one thing: 

https://flagit-admin.<tailnet>.ts.net/  →  http://flagit:3000

Its whole configuration is deploy/tailscale/serve.json, handed to the container through TS_SERVE_CONFIG: 

{
  "TCP": { "443": { "HTTPS": true } },
  "Web": {
    "${TS_CERT_DOMAIN}:443": {
      "Handlers": { "/": { "Proxy": "http://flagit:3000" } }
    }
  },
  "AllowFunnel": { "${TS_CERT_DOMAIN}:443": false }
}

A few of those choices matter. ${TS_CERT_DOMAIN} is substituted by the container with the node's own name, so the file never hardcodes a tailnet. The proxy target is the compose service name rather than localhost, because the sidecar is a separate container — which is also why TS_ACCEPT_DNS stays false: MagicDNS would displace Docker's resolver and flagit would stop resolving. The directory is mounted, not the file, so tailscaled sees edits. And Funnel is denied in writing.

Three one-time things on the tailnet before the first deploy:

  1. Enable HTTPS certificates (admin console → DNS → HTTPS Certificates). Without them there is no certificate for port 443 and the node comes up unreachable.
  2. Create an auth key (Settings → Keys). Tag it, for example tag:flagit-admin, so the node is exempt from key expiry; the tag needs an owner in your ACL policy. Pass it as the TS_AUTHKEY secret. It is consumed on first start — after that the identity lives in the tailscale_state volume.
  3. Check your ACLs if they are not default-allow: the devices that should reach the dashboard need access to flagit-admin on port 443.

The dashboard is then at https://flagit-admin.<tailnet>.ts.net/internal/admin, reachable from your devices and nothing else. Revoking the node in the admin console takes the dashboard offline without touching the public API or any other machine on the tailnet.

Running Tailscale on the host instead. Installing tailscale on the VM and running tailscale serve --bg 3000 also works, but only if the admin port is published to the host — which this deployment deliberately does not do. The sidecar keeps that port off the host entirely.

Public: the API over Funnel

An alternative to the Coolify route above, for when you do not want a domain of your own. Use one or the other, not both. 

# Expose only the public port to the internet, with TLS handled for you
tailscale funnel --bg 8080

Funnel gives you an HTTPS hostname on ts.net. Set FLAGIT_PUBLIC_URL to it so webhook payloads carry a working ticket link.

Funnel exposes exactly one port. Point it at 8080 and never at 3000. Funnel requires HTTPS enabled on the tailnet and the node tagged for funnel use; check tailscale funnel status if the hostname does not resolve.

Bare binary

No Docker anywhere in sight:

make web      # build the Svelte bundles and stage them for embedding
make build    # produce bin/flagit with the frontend inside

./bin/flagit --db-path /var/lib/flagit/flagit.db \
             --public-url https://flagit.example.com

A minimal systemd unit:

[Unit]
Description=Flagit
After=network-online.target

[Service]
User=flagit
Environment=FLAGIT_PUBLIC_URL=https://flagit.example.com
ExecStart=/usr/local/bin/flagit --db-path /var/lib/flagit/flagit.db
Restart=on-failure
StateDirectory=flagit

[Install]
WantedBy=multi-user.target

Both servers shut down gracefully on SIGTERM: in-flight requests get 15 seconds, and outbound Hermes webhooks get a further 20 to drain rather than being dropped.

Operating

Backups

The entire state is one SQLite file. Copy it with SQLite's own backup so you never capture a half-written transaction: 

docker compose exec flagit /bin/sh -c \
  'sqlite3 /data/flagit.db ".backup /data/backup.db"' || \
docker compose cp flagit:/data/flagit.db ./flagit-backup.db

The Alpine runtime image is deliberately minimal and has no sqlite3 binary, so in practice: stop the container, copy the file, start it again. Downtime is a second or two.

Upgrades

git pull
docker compose up -d --build

Schema migrations run automatically at startup. The admin key survives an upgrade — its hash is stored in the database, not baked into the image.

Lost the admin key?

Nothing can recover it; only the hash is stored. Set FLAGIT_ADMIN_KEY to a new value and restart — the new key is hashed and replaces the old one.

Checking it is alive

curl -s http://127.0.0.1:8080/healthz
{"data":{"status":"ok"}}

Both routers answer /healthz without a credential, so uptime monitoring needs no secrets.
